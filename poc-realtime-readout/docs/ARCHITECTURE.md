# 구조와 계산 방법

## 데이터 흐름

```
data/raw (본사)  ─┐
data/collected   ─┼─ io.load_all() ── schema.coerce() ── analysis/* ── build.py ── readout.json ── web (정적)
data/generated   ─┘   테이블별로 먼저 있는 곳을 씀       열·타입 검사     판독 시점별 계산
```

- 계산은 전부 파이썬에 있고 `tests/`로 검증한다. 웹은 JSON을 그리기만 한다.
- 판독 시점(`config.VIEWS`)마다 **그 날까지의 데이터만** 써서 기준선·ROI·순위를 다시 계산한다.
  그래서 1주차 판독과 월말 판독의 숫자가 다르고, 이것이 '주간 판독'의 시연 포인트다.

## 계산

### 기준선 (행사가 없었을 때의 판매) — `analysis/baseline.py`

이달의 맛은 출시 전 이력이 없어서 둘로 나눠 잡는다.

1. **요일 패턴**: 기존 맛의 출시 전 4주 판매에서 추정 (주 단위 추세를 빼고 요일별 평균 잔차).
2. **추세**: 이달의 맛의 행사 없는 날 판매를 요일 패턴으로 나눈 뒤 `c0 + c1·exp(−t/k)` 로 맞춤.
   k는 격자 탐색(3~80일), c0·c1은 최소제곱. 비슷하게 잘 맞는 k 전체로 기준선 범위(위·아래)를 낸다.

k < 3 은 제외했다. 1주차처럼 행사 없는 날이 5일뿐일 때 '사흘 만에 반응이 다 빠지는' 곡선이 행사일 기준선을 마음대로 키우기 때문.

### 판촉 효과 — `analysis/promo.py`

- 증분 = 행사 기간 판매 − 기준선
- 증분 ROI = 증분 매출 ÷ 할인 비용 = 증분 개수 ÷ (행사 기간 판매 × 할인 환산율). 단가는 약분된다.
- 판정: 1.3 이상 지속, 1.0~1.3 조정, 1.0 미만 중단 검토 (`config.RULES`)
- **잠정**: 기준선을 맞춘 행사 없는 날이 10일 미만이거나, ROI 범위 양 끝의 판정이 다르면.

목 데이터 기준 정답 대비 오차는 3~4% (테스트에서 10% 이내 확인).

### 매장 — `analysis/stores.py`

- 순위 = 판독 주간 일평균 판매(전 맛 합계)의 전국 순위. 변화 = 직전 판독 주간 대비.
- 신호: `반응↑ 판매↓ 점검` = 주변 언급 15건 이상 & +60% 이상 & 순위 100 이상 하락 → 품절·운영 의심.
  `확산` = 순위 100 이상 상승.
- **왜**: ① 상권 맥락(유동인구, 경쟁점 개점) → ② 점검 신호 → ③ 지난 판독 점검 매장의 회복 →
  ④ 그 유형 매장 전체가 같은 방향으로 움직였으면 '유형 전반' → 없으면 '개별 요인 · 확인 필요'.
- 유형별 판매 몰림: 유형 매장당 판매 ÷ 전체 매장당 판매(3일 이동평균)가 가장 높은 날. 검색 반응 정점과의 시차를 같이 표시.

### 결정 카드 — `analysis/cards.py`

판정 기준은 `config.RULES` 한곳에. 문구도 파이썬에서 만들어 JSON으로 넘긴다(웹에 로직을 두지 않기 위해).

## 확장 지점

| 하고 싶은 것 | 고칠 곳 |
|---|---|
| 다음 달 이달의 맛으로 바꾸기 | `config.Launch`, `config.VIEWS`, 행사표 CSV |
| 판정 기준 바꾸기 | `config.Rules` |
| 본사 데이터 연결 | `data/raw/*.csv` (열은 `schema.py`) |
| 새 반응 소스 추가 | `collect/`에 수집기 → `reaction_daily` 형식(long)으로 → `build.py` series 키 추가 |
| LLM 요약 문구 | `cards.py` 결과를 입력으로 한 줄 요약 생성 (팀 PoC의 `agents/llm.py` 어댑터 패턴 참고). 판정은 규칙으로, 문장만 LLM으로 |

## 배포

`make web` → `web/dist`(정적 파일). 서버·DB가 없다.
CI(`.github/workflows/ci.yml`)는 PR마다 테스트 + JSON 빌드 + 웹 타입체크·빌드를 돌린다.
