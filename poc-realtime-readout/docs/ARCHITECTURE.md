# 구조와 계산 방법

## 데이터 흐름

```
data/raw (본사)  ─┐
data/collected   ─┼─ io.load_all() ── schema.coerce() ── build.py: 하루씩 진행 ──────────── readout.json ── web
data/generated   ─┘   테이블별로 먼저 있는 곳          열·타입 검사   d일까지의 데이터로              (정적)
                                                                      기준선·순위·주제·전환 계산
                                                                      → alerts.Tracker.step(d)
                                                                      → 카드 4장
```

- 슬라이더의 하루 d = d일 밤까지 쌓인 데이터를 d+1일 아침에 본 판독. 계산은 d일까지의 데이터만 쓴다.
  `tests/test_analysis.py::test_no_future_data`가 데이터를 3/12에서 잘라 다시 돌려도 3/12까지의 알림·카드가 같은지 확인한다.
- 계산은 전부 파이썬에 있고 웹은 그리기만 한다. 판정 기준과 알림 기준은 `config.Rules` 한곳에.

## 실시간 감지 — `analysis/alerts.py`

| 신호 | 기준 (config.Rules) | 할 일 예시 |
|---|---|---|
| 검색 급등 | 검색지수 ≥ 출시 전 한 달 평균 × 5 | 출시일 콘텐츠·광고 집행 앞당김, 초도 물량 점검 |
| 검색 정점 통과 | 출시 후 최고점에서 이틀 이상 지나 15% 넘게 하락 | 확산기 → 유지기, 전환·재구매 신호로 관점 전환 |
| 업계 키워드 하락 | 유행 키워드가 3주 전보다 40% 이상 하락 | 유행 편승 문구 줄이고 맛으로 소구 |
| 영상 조회 돌파 | 영상 조회수가 100만·300만 회를 넘김 (원값) | 소비자 영상 리포스트·크리에이터 협업, 영상 속 조합을 POP로 |
| 주제 언급 급증 | 최근 3일 주제 비중 ≥ 그 전 14일의 2배, 150건 이상 (행사 중 가격·사이즈 언급은 제외) | 품절 → 재고 확인·공지, 비교 → 차별점 콘텐츠 |
| 주제 부정 증가 | 주제 긍정률이 그 전 14일보다 15%p 이상 하락 | 맛 → 페어링·토핑 안내, 다음 맛 레시피 반영 |
| 전체 긍정률 하락 | 최근 3일이 그 전 7일보다 5%p 이상 하락 | 어떤 주제가 끌어내렸는지 확인 |
| 첫 주 판독 | 출시 7일째, 맛 수요 ÷ 목표 | 증산 / 유지 / 감산 |
| 매장 점검·바이럴 | 아래 '매장' 참고 | 재고·운영 확인 / 재고 선배치·콘텐츠 확산 |
| 행사 판독 | 행사가 끝나고 기준선을 맞출 수 있게 된 첫날 | 지속 / 조정 / 중단 검토 |
| 반응 대비 판매 | 판매 지수 ÷ 검색 지수 ≥ 1.5 또는 ≤ 0.8 (출시 첫 주 = 100) | 광고는 재방문 쪽으로 / 품절·가격·접근성 점검 |

같은 신호가 며칠 연속 울리지 않게 신호별 대기 기간을 둔다. 알림마다 "지금 방식(월말 정산 후 4/6 판독, 가정)보다 며칠 빨리 봤는지"를 붙인다.
카드의 '반응 대응'은 최근 3일 알림 중 가장 급한 것(즉시 대응 > 대응 검토 > 확산 활용 > 관찰)을 올린다.

## 계산

### 기준선 (행사가 없었을 때의 판매) — `analysis/baseline.py`

이달의 맛은 출시 전 이력이 없어서 둘로 나눠 잡는다.

1. **요일 패턴**: 기존 맛의 출시 전 4주 판매에서 추정.
2. **추세**: 이달의 맛의 행사 없는 날 판매를 요일 패턴으로 나눈 뒤 `c0 + c1·exp(−t/k)` 로 맞춤.
   k는 격자 탐색(3~80일), c0·c1은 최소제곱. 비슷하게 잘 맞는 k 전체로 기준선 범위를 낸다.

출시일이 배라데이와 겹쳐 3/1~3/3은 기준선을 못 맞춘다. 행사 없는 날이 3일 쌓인 3/6부터 배라데이를 판독하고, 10일 미만이면 '잠정'.

### 판촉 효과 — `analysis/promo.py`

- 증분 = 행사 기간 판매 − 기준선. 증분 ROI = 증분 개수 ÷ (행사 기간 판매 × 할인 환산율). 단가는 약분된다.
- 판정: 1.3 이상 지속, 1.0~1.3 조정, 1.0 미만 중단 검토. 기준선 근거 10일 미만이거나 ROI 범위가 기준을 걸치면 '잠정'.
- 목 데이터 기준 정답 대비 오차 3~4% (테스트에서 10% 이내 확인).

### 매장 — `analysis/stores.py`

- 순위 = 최근 7일 일평균 판매(전 맛 합계)의 전국 순위, 변화 = 그 전 7일 대비.
- **주변 언급↑**: 7일 15건 이상, 10건 이상 늘었고, 전국 언급 흐름보다 60% 이상 더 늘어남
  (출시 직후처럼 전 매장 언급이 같이 뛰는 것은 신호가 아님. 적은 건수의 배수 폭증을 막으려고 양쪽에 5건씩 더해 배수를 잰다).
- 점검 = 주변 언급↑ + 순위 100 이상 하락. 바이럴 = 주변 언급↑ + 순위 100 이상 상승. 회복 = 최근 2주 안에 점검이었던 매장의 순위 회복.
- 반응 변화 없이 판매만 움직인 매장은 '확인 필요'로 둔다.

### 반응 — `analysis/reaction.py`

- 주제: 최근 3일 언급·긍정률, 그 전 14일 대비 비중 변화. 주제 분류는 블로그·카페 요약문 단어 사전(`collect/naver.py`의 `TOPIC_WORDS`).
- 전환: 출시 첫 주 평균을 100으로 맞춘 판매 지수와 검색 지수(최근 7일 평균)의 비. 출시 2주 차부터.
- 유튜브: 영상별 조회수 원값만. 합계·비율·증가량 같은 파생 지표는 만들지 않는다(API 정책).

## 실제 운영으로 넘어갈 때

| 하고 싶은 것 | 고칠 곳 |
|---|---|
| 매일 아침 자동 판독 | `make collect && make build-data`를 스케줄러(예: GitHub Actions cron)로 매일 실행 → `web/dist` 재배포 |
| 시간 단위 감지 | 유튜브·블로그는 시간 단위 수집 가능. `asof_dates()`를 시간 단위로, 알림 기준 창(3일·14일)을 시간에 맞게 조정 |
| 다음 달 이달의 맛 | `config.Launch`(이름·출시일·목표), 행사표 CSV |
| 판정·알림 기준 | `config.Rules` |
| 본사 데이터 연결 | `data/raw/*.csv` (열은 `schema.py`) |
| 알림 문구를 자연어로 다듬기 | `alerts.py` 결과를 입력으로 문장만 LLM으로 생성 (판정은 규칙으로 유지) |

CI(`.github/workflows/ci.yml`)는 PR마다 테스트 + JSON 빌드 + 웹 타입체크·빌드를 돌린다.
